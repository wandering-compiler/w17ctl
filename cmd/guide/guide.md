# AGENTS.md — working in a w17 project with w17ctl

You are a coding agent in a **wandering-compiler (w17)** project. w17 is a
**declarative compiler**: you describe schemas, DB models, queries, events, and
APIs as proto + annotations, and the `w17ctl` CLI generates the gRPC binaries,
DB access layer, plain-SQL migrations, gateways (REST/SSE/WS/MCP), clients, and
deploy config. **The only code you hand-write is the body of gRPC business
handler methods.** Everything else is generated — do not write DB or gRPC
plumbing by hand.

> **Before you design anything, read `w17/specs/`** — the w17 **platform
> reference** (server-generated, so it always matches the compiler): the
> annotation catalog (`w17/specs/annotations.md`), how APIs are generated + the
> Query/Mutation/Service/Facade model + the event system + directory structure
> (`w17/specs/architecture.md`), and the escape hatches. AGENTS.md (this file) is
> *how to drive the tool*; `w17/specs/` is *how the technology works*.
>
> **If `w17/specs/` isn't present yet**, run `w17ctl login` then `w17ctl guide` to
> fetch it — it's generated by the compiler, so it needs a reachable console
> (unlike this file, which ships with the client). Do that before designing.

## The golden rules

1. **Declare, then generate.** To add or change behaviour, edit the `.proto`
   under `proto/` and run `w17ctl codegen` — never hand-edit generated files.
2. **Generated files are `DO NOT EDIT`.** Anything under the generated-code dir
   (bundles, pb stubs, clients) is overwritten on every codegen. Your edits go
   only in hand-written business-handler bodies.
3. **Learn the annotations from the tool.** `w17ctl template <surface>` prints a
   commented example proto for any surface (types, queries, mutations, business,
   rest, admin, events, rpc, mcp, cli). Use it instead of guessing annotations.
4. **When unsure, ask the CLI.** Every command has `w17ctl <command> --help`.

## What w17ctl is

`w17ctl` is the single CLI + entrypoint for this project. It is a thin client:
it talks to a **console** backend (which does all the compiling / migration
planning), reads and writes your local files, and drives docker. You never run a
compiler directly — you drive `w17ctl`.

## The canonical workflow

```
1. w17ctl guide                 # (this file) orient yourself — run first
2. w17ctl init                  # bootstrap a new project (writes w17/lock.yaml)
3. w17ctl domain add <name>     # scaffold a domain (--with-example for a full sample)
   w17ctl module add <domain> <name>
4. edit proto/domains/<domain>/… # declare models/queries/mutations/events
   (use `w17ctl template <surface>` to see the annotation shapes)
5. w17ctl codegen               # generate all derived code + the project map
6. w17ctl migrate generate      # plan the SQL migrations from the schema
7. w17ctl stack up              # bring up the local docker stack
8. …write business-handler bodies… then re-run codegen as the schema evolves
9. w17ctl test --target <url>   # run the generated e2e suite against the gateway
10. w17ctl stress <url>         # load-test the gateway with the generated stress presets
```

## Command cheat-sheet (task → command)

| You want to… | Run |
|---|---|
| Start a new project | `w17ctl init` |
| See how to annotate a surface | `w17ctl template <surface>` (`--list`) |
| Add a domain / module | `w17ctl domain add` / `w17ctl module add` |
| Add a DB/store connection | `w17ctl connection add` |
| Install a plugin (auth, …) | `w17ctl plugin install <name>` |
| Generate all code | `w17ctl codegen` |
| Check for generated-vs-proto drift (CI) | `w17ctl verify` |
| Plan / list migrations | `w17ctl migrate generate` / `migrate list` |
| Seed fixtures | `w17ctl fixtures …` |
| Run the local stack | `w17ctl stack up` / `down` / `logs` |
| Run the e2e suite | `w17ctl test --target <url>` |
| Load-test a gateway | `w17ctl stress <url>` (`--preset` for one preset; `-c/-d/-n` to override the plan) |
| Snapshot / switch dev DB | `w17ctl db snapshot …` |
| Review a schema change (PR flow) | `w17ctl review open` → `approve` → `merge` |
| Check compatibility of a change | `w17ctl compat report …` |
| Manage deploy environments | `w17ctl env …` |
| Log in to a console | `w17ctl login` |
| Remove generated output | `w17ctl clean` |

## Where to make changes

- **Proto (`proto/…`)** — the source of truth. Declare here; regenerate.
- **Hand-written business bodies** — the only code you author. After the first
  `w17ctl codegen`, a **generated symbol map** appears at `w17/AGENTS.md` +
  `w17/map/`: grep it to find where a thing lives, and look for `EDIT-HERE=<file>`
  to locate the hand-written handler body you should edit (`EDIT-HERE=gen=…` is
  generated — don't touch it; `EDIT-HERE=none` is plugin-owned — change behaviour
  via the proto `plugins.features`, not code).
- **Never** edit generated bundles, pb stubs, clients, or migration SQL by hand.
